# ice-pos-web Constitution (ธรรมนูญการพัฒนาระบบส่วนหน้าบ้าน)

## 1. วัตถุประสงค์และขอบเขต

เอกสารฉบับนี้กำหนดหลักการและมาตรฐานกลางสำหรับการพัฒนาระบบส่วนหน้าบ้าน (Frontend) สำหรับโปรเจกต์ ice-pos-web เพื่อให้ซอฟต์แวร์มีคุณภาพ ปลอดภัย ใช้งานง่าย บำรุงรักษาได้ และสามารถขยายระบบในอนาคตได้

ธรรมนูญนี้สามารถใช้กับโปรเจกต์หลากหลายประเภท เช่น Web Application, Mobile Application, Desktop Application, Dashboard, E-Commerce และระบบภายในองค์กร โดยไม่จำกัดภาษาโปรแกรม Framework หรือเทคโนโลยี Backend

หลักการทั้งหมดต้องปรับใช้ให้เหมาะสมกับบริบท ข้อกำหนด และข้อจำกัดของแต่ละโปรเจกต์ โดยไม่สร้างความซับซ้อนเกินความจำเป็น

## 2. หลักการใช้ภาษา

### 2.1 ใช้ภาษาไทยเป็นหลัก
- การสื่อสารกับผู้ใช้ การอธิบายแนวทางพัฒนา การวิเคราะห์ปัญหา การสรุปงาน และการรายงานผล ต้องใช้ภาษาไทยเป็นหลัก
- เอกสารประกอบโปรเจกต์ เช่น Requirements, Architecture, Technical Specifications และคู่มือการใช้งาน ให้เขียนเป็นภาษาไทยเป็นหลัก
- คำอธิบายโค้ด (Code Comments) และเอกสารทางเทคนิคภายในโปรเจกต์ ให้ใช้ภาษาไทยเมื่อสามารถอธิบายได้อย่างชัดเจน
- ข้อความบนส่วนติดต่อผู้ใช้ (UI Text) ให้ใช้ภาษาตามข้อกำหนดของโปรเจกต์ หากไม่ได้ระบุ ให้ใช้ภาษาไทยเป็นค่าเริ่มต้นสำหรับระบบที่มุ่งเน้นผู้ใช้ภาษาไทย
- ห้ามเปลี่ยนไปใช้ภาษาอังกฤษทั้งหมดโดยไม่มีเหตุผลหรือข้อกำหนดรองรับ

### 2.2 อนุญาตให้ใช้ภาษาอังกฤษและคำทับศัพท์
สามารถใช้ภาษาอังกฤษหรือคำทับศัพท์ได้เมื่อช่วยให้การสื่อสารแม่นยำ กระชับ หรือเป็นไปตามมาตรฐานทางเทคนิค เช่น:
- ชื่อทางเทคนิค เช่น `Function`, `Class`, `Interface`, `Component` และ `Middleware`
- ชื่อภาษาโปรแกรม Framework, Library, Package และเครื่องมือ
- ชื่อมาตรฐานและแนวคิด เช่น `REST API`, `Dependency Injection`, `Clean Architecture` และ `State Management`
- ชื่อไฟล์ ตัวแปร ฟังก์ชัน คลาส เมธอด และ API Endpoint ที่ต้องตรงกับ Source Code หรือข้อกำหนดจริง
- คำศัพท์ทางเทคนิคที่แปลเป็นภาษาไทยแล้วอาจทำให้ความหมายคลาดเคลื่อน

เมื่อใช้คำศัพท์เฉพาะเป็นครั้งแรก สามารถระบุคำอธิบายภาษาไทยกำกับเพื่อให้เข้าใจได้ง่ายขึ้น ตัวอย่าง:
- Dependency Injection (การส่งต่อสิ่งที่ส่วนประกอบต้องพึ่งพา)
- State Management (การจัดการสถานะของระบบ)
- Error Handling (การจัดการข้อผิดพลาด)
- Responsive Design (การออกแบบให้ปรับตามขนาดหน้าจอ)

### 2.3 รักษาชื่อทางเทคนิคให้ตรงกับระบบจริง
- ห้ามแปลหรือเปลี่ยนชื่อ `Function`, `Class`, `Variable`, `Method`, `Package`, `API Field` หรือชื่อทางเทคนิคที่ต้องตรงกับโค้ดจริง
- ชื่อใน Source Code ต้องเป็นไปตามหลักการตั้งชื่อของภาษาและ Framework ที่ใช้
- สามารถใช้ภาษาอังกฤษในโค้ดได้ตามมาตรฐานของภาษาโปรแกรมนั้น
- การใช้ภาษาไทยเป็นหลักไม่ใช่ข้อกำหนดให้ใช้ภาษาไทยใน Identifier หรือชื่อทางเทคนิคที่ต้องอ้างอิงจากระบบจริง

## 3. หลักการพัฒนาซอฟต์แวร์ (Core Principles)

### 3.1 ความถูกต้องต้องมาก่อนความรวดเร็ว (Correctness Over Speed)
- พัฒนาระบบให้ตรงตามข้อกำหนดและพฤติกรรมที่ตกลงกันไว้
- ห้ามสร้างข้อมูล ข้อกำหนด API หรือกฎทางธุรกิจขึ้นเองโดยไม่มีหลักฐานรองรับ
- ตรวจสอบแหล่งข้อมูลที่เกี่ยวข้องก่อนตัดสินใจด้านเทคนิค
- หากมีประเด็นคลุมเครือที่กระทบต่อความถูกต้อง ความปลอดภัย หรือข้อมูลสำคัญ ต้องขอคำชี้แจงก่อนดำเนินการ
- ห้ามใช้วิธีแก้ไขชั่วคราวที่ทำให้ข้อมูลผิดพลาดหรือซ่อนปัญหาที่แท้จริง

### 3.2 ความเรียบง่ายและความเหมาะสม (Simplicity & Appropriateness)
- เลือกวิธีแก้ปัญหาที่ตรงไปตรงมา เข้าใจง่าย และเหมาะสมกับขนาดของระบบ
- หลีกเลี่ยงการออกแบบที่ซับซ้อนเกินความจำเป็น
- ไม่เพิ่ม Abstraction, Dependency หรือ Design Pattern โดยไม่มีเหตุผลรองรับ
- ไม่สร้างระบบกลางเพื่อรองรับกรณีสมมติที่ยังไม่มีความจำเป็น
- ให้ความสำคัญกับความชัดเจนในการอ่าน การแก้ไข และการทดสอบโค้ด

### 3.3 รักษาความสามารถเดิมของระบบ (Preserve Existing Functionality)
- ก่อนแก้ไขโค้ด ต้องตรวจสอบโครงสร้างและพฤติกรรมเดิมที่เกี่ยวข้อง
- การแก้ไขต้องไม่ทำให้ฟังก์ชันที่มีอยู่เสียหายโดยไม่ตั้งใจ
- หลีกเลี่ยงการแก้ไขไฟล์หรือโมดูลที่ไม่เกี่ยวข้องกับงาน
- หากจำเป็นต้องเปลี่ยนพฤติกรรมเดิม ต้องระบุผลกระทบและเหตุผลให้ชัดเจน
- การ Refactor ต้องรักษาพฤติกรรมเดิม เว้นแต่ข้อกำหนดจะระบุให้เปลี่ยนแปลง

## 4. สถาปัตยกรรมและโครงสร้างโค้ด

### 4.1 การแยกความรับผิดชอบ (Separation of Concerns)
- แยกส่วนแสดงผล ตรรกะทางธุรกิจ การจัดการสถานะ และการเข้าถึงข้อมูลตามความเหมาะสม
- แต่ละโมดูลหรือ Component ควรมีหน้าที่ชัดเจน
- หลีกเลี่ยงการรวมความรับผิดชอบหลายประเภทไว้ในส่วนเดียวจนยากต่อการบำรุงรักษา
- ส่วนแสดงผลไม่ควรรับผิดชอบตรรกะทางธุรกิจที่ซับซ้อนโดยไม่จำเป็น
- แยกการเชื่อมต่อกับระบบภายนอกออกจากส่วนที่ไม่ควรผูกติดกับรายละเอียดการเชื่อมต่อ

### 4.2 การจัดระเบียบโค้ด (Code Organization)
- ใช้โครงสร้างโฟลเดอร์และแนวทางการตั้งชื่อที่สม่ำเสมอ
- ตั้งชื่อไฟล์ คลาส ฟังก์ชัน ตัวแปร และ Component ให้สื่อความหมาย
- แบ่งโค้ดเป็นส่วนย่อยตามหน้าที่และความรับผิดชอบ
- หลีกเลี่ยงโค้ดซ้ำ หากสามารถใช้วิธีร่วมกันที่อ่านง่ายและเหมาะสมได้
- ใช้ค่าคงที่และการตั้งค่าจากส่วนกลางเมื่อเหมาะสม
- ปฏิบัติตามมาตรฐานของภาษาโปรแกรมและ Framework ที่โปรเจกต์เลือกใช้

### 4.3 เครื่องมือควบคุมคุณภาพโค้ด (Code Quality Tooling)
- ใช้ Formatter, Linter และ Static Analysis ตามความเหมาะสม
- รักษาความสม่ำเสมอของรูปแบบโค้ดทั้งระบบ
- หลีกเลี่ยงการปิดกฎตรวจสอบหรือซ่อน Warning โดยไม่มีเหตุผลที่ชัดเจน

## 5. การจัดการข้อมูลและการเชื่อมต่อระบบ

### 5.1 แหล่งข้อมูลและสัญญาการเชื่อมต่อ (Data Sources & API Contracts)
- ใช้เอกสาร API, Schema, Interface และข้อกำหนดที่ได้รับการยืนยันเป็นแหล่งอ้างอิง
- ห้ามคาดเดา Endpoint ชื่อฟิลด์ ชนิดข้อมูล รูปแบบ Response หรือพฤติกรรมของระบบภายนอก
- ห้ามทำการจำลองข้อมูลขึ้นเอง (No Ad-hoc Mock Data): ให้ใช้ข้อมูลที่ได้รับจาก API จริงเป็นหลัก หากไม่พบ Endpoint หรือไม่แน่ใจเรื่อง API ให้ทำการสอบถามเพื่อขอความชัดเจนก่อนดำเนินการเสมอ
- กรณีปรับแก้หน้าบ้านแล้วมีผลกระทบหรือต้องปรับแก้ API: ให้ทำการสรุปเป็นไฟล์เอกสาร ระบุรายละเอียดสิ่งที่ต้องเพิ่มหรือปรับแก้ (เช่น Endpoint, Parameters, Request/Response Schema, Status Code) อย่างชัดเจน เพื่อให้ทีม API นำไปปรับแก้หรือเพิ่มเติมต่อไป
- แยกการเข้าถึงข้อมูลออกจากส่วนแสดงผลตามความเหมาะสม
- ตรวจสอบและแปลงข้อมูลภายนอกก่อนนำไปใช้งาน
- จัดการข้อมูลที่หายไป ไม่ถูกต้อง หรือไม่เป็นไปตามรูปแบบที่คาดหวังอย่างชัดเจน

### 5.2 การจัดการสถานะข้อมูล (State Management)
- แยกสถานะการแสดงผลออกจากข้อมูลธุรกิจตามความเหมาะสม
- กำหนดสถานะ Loading, Success, Empty และ Error ให้ชัดเจน
- ป้องกันการใช้ข้อมูลเก่าหรือข้อมูลที่ไม่สอดคล้องกับสถานะปัจจุบันโดยไม่ตั้งใจ
- จัดการคำขอที่ทำงานพร้อมกันและการตอบกลับล่าช้าเมื่อจำเป็น
- หลีกเลี่ยงการเรียกข้อมูลซ้ำโดยไม่จำเป็น
- จัดการทรัพยากรที่ต้องคืนหรือปิดเมื่อเลิกใช้งาน

### 5.3 ความถูกต้องของข้อมูล (Data Integrity)
- รักษาความถูกต้องและความสอดคล้องของข้อมูลตลอดกระบวนการทำงาน
- ใช้ชนิดข้อมูลและวิธีคำนวณที่เหมาะสมกับลักษณะข้อมูล
- หลีกเลี่ยงการแปลงข้อมูลที่ทำให้ความหมายหรือความแม่นยำเปลี่ยนไปโดยไม่ตั้งใจ
- การคำนวณและการตรวจสอบที่สำคัญต้องเป็นไปตามข้อกำหนดของระบบ
- ห้ามรายงานว่าการดำเนินการสำเร็จ หากยังไม่ได้รับผลยืนยันที่เพียงพอ
- หากการดำเนินการสำเร็จเพียงบางส่วน ต้องแสดงและจัดการสถานการณ์ดังกล่าวอย่างถูกต้อง

## 6. มาตรฐาน UI/UX

### 6.1 ความสม่ำเสมอของส่วนติดต่อผู้ใช้ (UI Consistency)
- ใช้แนวทางการออกแบบ สี ตัวอักษร ระยะห่าง และรูปแบบ Component อย่างสม่ำเสมอ
- สร้าง Component ที่ใช้ซ้ำร่วมกันเมื่อช่วยลดความซ้ำซ้อนและทำให้ระบบดูแลรักษาง่ายขึ้น
- รักษาความสม่ำเสมอของปุ่ม ฟอร์ม ตาราง กล่องข้อความ และองค์ประกอบที่มีลักษณะคล้ายกัน
- ไม่สร้างรูปแบบใหม่ที่ขัดแย้งกับระบบออกแบบเดิมโดยไม่มีเหตุผล

### 6.2 ความง่ายในการใช้งาน (Usability)
- ออกแบบหน้าจอให้ผู้ใช้เข้าใจได้โดยไม่ต้องคาดเดาพฤติกรรมของระบบ
- ใช้ข้อความ ป้ายกำกับ และคำแนะนำที่ชัดเจน
- จัดลำดับความสำคัญของข้อมูลและการดำเนินการตามลักษณะงาน
- ลดขั้นตอนที่ไม่จำเป็นและป้องกันการกระทำผิดพลาดเมื่อทำได้
- ให้ข้อมูลตอบกลับที่เหมาะสมหลังผู้ใช้ดำเนินการ
- การดำเนินการที่มีผลกระทบสูงควรมีมาตรการป้องกันที่เหมาะสม

### 6.3 การรองรับหน้าจอและแพลตฟอร์ม (Responsive & Cross-Platform)
- หากระบบรองรับหลายขนาดหน้าจอ ต้องออกแบบให้เนื้อหาและการทำงานเหมาะสมกับแต่ละขนาด
- หากระบบรองรับหลายแพลตฟอร์ม ต้องคำนึงถึงรูปแบบการใช้งานและข้อจำกัดของแต่ละแพลตฟอร์ม
- หลีกเลี่ยงการกำหนดขนาดตายตัวที่ทำให้เนื้อหาล้นหรือใช้งานไม่ได้
- ตรวจสอบการใช้งานด้วยเมาส์ คีย์บอร์ด และหน้าจอสัมผัสตามความเหมาะสม
- ไม่จำเป็นต้องรองรับแพลตฟอร์มที่อยู่นอกขอบเขตของโปรเจกต์

### 6.4 การเข้าถึงสำหรับผู้ใช้ทุกกลุ่ม (Accessibility)
- ใช้สีและความแตกต่างขององค์ประกอบที่ช่วยให้อ่านได้ชัดเจน
- ไม่ใช้สีเพียงอย่างเดียวในการสื่อความหมายที่สำคัญ
- กำหนดชื่อหรือคำอธิบายให้กับองค์ประกอบที่ต้องอาศัยเทคโนโลยีช่วยเหลือเมื่อเหมาะสม
- รองรับการใช้งานด้วยคีย์บอร์ดและการนำทางที่เข้าถึงได้ตามความสามารถของแพลตฟอร์ม

### 6.5 การออกแบบที่เหมาะสมกับผู้สูงอายุและการสัมผัส (Elderly-Friendly & Touchscreen Design)
- **ขนาดเป้าหมายการสัมผัส (Touch Targets)**: ปุ่มกด (Buttons), ช่องเลือก (Dropdowns/Selects), สวิตช์สลับ (Toggles) และองค์ประกอบที่โต้ตอบได้ ต้องมีขนาดไม่เล็กกว่า 48x48px (หรืออย่างน้อย 44x44px สำหรับองค์ประกอบรอง) พร้อมระยะห่างระหว่างองค์ประกอบที่เพียงพอ (อย่างน้อย 8-12px) เพื่อป้องกันการแตะพลาดจากอาการมือสั่นหรือความแม่นยำในการสัมผัสที่ลดลง
- **ขนาดตัวอักษรและความชัดเจนในการอ่าน (Typography & Legibility)**:
  - ตัวอักษรข้อความทั่วไปต้องมีขนาดไม่เล็กกว่า 16px (1rem) เพื่อให้อ่านง่ายโดยไม่ต้องเพ่ง
  - หัวข้อ ป้ายกำกับสำคัญ และตัวเลขราคา/ยอดเงิน ต้องมีขนาดใหญ่ ชัดเจน และมีน้ำหนักตัวอักษรที่เด่นชัด (Bold/Semibold)
  - ใช้แบบอักษรที่อ่านง่าย มีหัวชัดเจน หลีกเลี่ยงตัวอักษรบางเฉียบ (Thin/Light) และตัวเอียง
- **ความคมชัดและคอนทราสต์ของสี (High Contrast Ratio)**:
  - อัตราส่วนความคมชัดระหว่างตัวอักษรและพื้นหลัง (Contrast Ratio) ต้องผ่านเกณฑ์ WCAG 2.1 AA เป็นอย่างน้อย (ไม่ต่ำกว่า 4.5:1 สำหรับข้อความขนาดปกติ และไม่ต่ำกว่า 3:1 สำหรับข้อความขนาดใหญ่หรือตัวเลขสำคัญ)
  - ห้ามใช้ตัวอักษรสีเทาจาง (Faint Gray) บนพื้นหลังสีมืดหรือสีขาว
  - สถานะสำคัญ (เช่น สำเร็จ, คำเตือน, ข้อผิดพลาด) ต้องใช้ทั้งสี ไอคอน และข้อความกำกับร่วมกันเสมอ ไม่ใช้สีเพียงอย่างเดียว
- **ช่องป้อนข้อมูลและแป้นตัวเลขสัมผัส (Input Fields & Touch Numeric Keypads)**:
  - ช่องกรอกข้อมูล (Input Fields) ต้องมีความสูงอย่างน้อย 48px มีเส้นขอบที่ชัดเจน (Clear Border) และแสดงสถานะ Focus/Active อย่างเด่นชัด
  - การป้อนจำนวนเงิน ราคา ปริมาณ รหัสบาร์โค้ด หรือรหัส PIN ต้องรองรับแป้นพิมพ์ตัวเลขสัมผัสขนาดใหญ่ (Virtual Numeric Keypad) บนหน้าจอสัมผัส POS เพื่อความสะดวกรวดเร็วในการป้อนข้อมูลโดยไม่ต้องต่อคีย์บอร์ดภายนอก
  - มีปุ่มล้างค่า (Clear) และปุ่มลบทีละหลัก (Backspace) ขนาดใหญ่ที่กดง่าย
- **การตอบสนองและการป้องกันข้อผิดพลาด (Immediate Feedback & Error Prevention)**:
  - ทุกการกดหรือสัมผัสต้องมีการตอบสนองทางสายตา (Visual Feedback) ชัดเจน เช่น การเปลี่ยนสีปุ่มทันที (Active/Pressed State)
  - กล่องข้อความแจ้งเตือน (Notifications / Modals) ต้องมีขนาดใหญ่ ใช้ภาษาไทยที่กระชับ ตรงไปตรงมา ชัดเจน ไม่ใช้ศัพท์เทคนิค
  - การกระทำที่มีผลกระทบสูง (เช่น การลบสินค้า, การยกเลิกบิล, การล้างรายการขาย) ต้องมีกล่องยืนยัน (Confirmation Dialog) พร้อมปุ่มยืนยันและยกเลิกขนาดใหญ่ที่มีสีแตกต่างกันอย่างเด่นชัด
- **การลดภาระการจดจำ (Low Cognitive Load & Visual Hierarchy)**:
  - จัดวางหน้าจอให้เรียบง่าย แสดงข้อมูลเฉพาะที่จำเป็นในแต่ละขั้นตอน ไม่ยัดเยียดข้อมูลหรือปุ่มกดจำนวนมากในหน้าจอเดียว
  - ลำดับขั้นตอนการทำงานให้เป็นเส้นตรง (Linear Flow) ไม่ซับซ้อน เข้าใจง่ายสำหรับผู้สูงวัย

## 7. ความปลอดภัยและความเป็นส่วนตัว (Security & Privacy)

- ห้ามฝัง Secret, Private Key, รหัสผ่าน หรือข้อมูลรับรองที่เป็นความลับไว้ใน Source Code หรือไฟล์ที่เผยแพร่ให้ผู้ใช้เข้าถึงได้
- จัดเก็บและส่งข้อมูลสำคัญด้วยวิธีที่เหมาะสมกับแพลตฟอร์มและระดับความเสี่ยง
- ห้ามบันทึกข้อมูลสำคัญลงใน Log โดยไม่จำเป็น
- ใช้การสื่อสารที่ปลอดภัยตามความเหมาะสมของระบบ
- ตรวจสอบและจัดการข้อมูลที่ผู้ใช้หรือระบบภายนอกส่งเข้ามา
- การซ่อนปุ่มหรือหน้าจอไม่ถือเป็นการควบคุมสิทธิ์ที่เพียงพอ
- การตรวจสอบสิทธิ์และการอนุญาตให้ดำเนินการที่สำคัญต้องบังคับใช้ในระบบที่เชื่อถือได้ตามสถาปัตยกรรม
- แสดงข้อผิดพลาดโดยไม่เปิดเผยข้อมูลภายในที่อาจก่อให้เกิดความเสี่ยง
- เก็บ ใช้ และส่งต่อข้อมูลส่วนบุคคลเท่าที่จำเป็นต่อวัตถุประสงค์ของระบบ

## 8. ประสิทธิภาพและการใช้ทรัพยากร (Performance & Resource Management)

- พิจารณาประสิทธิภาพให้เหมาะสมกับขนาดและลักษณะการใช้งานจริง
- หลีกเลี่ยงการคำนวณ การสร้าง Component และการร้องขอข้อมูลซ้ำโดยไม่จำเป็น
- จัดการหน่วยความจำและทรัพยากรอย่างเหมาะสม
- ใช้การแบ่งหน้า การโหลดข้อมูลตามความจำเป็น หรือการแคชเมื่อเหมาะสม
- หลีกเลี่ยงการเพิ่มประสิทธิภาพโดยไม่มีเหตุผลรองรับ หากทำให้โค้ดซับซ้อนขึ้นมาก
- ใช้เครื่องมือวัดผลเมื่อมีปัญหาหรือมีข้อกำหนดด้านประสิทธิภาพที่ชัดเจน

## 9. การจัดการข้อผิดพลาดและการบันทึกเหตุการณ์ (Error Handling & Logging)

- จัดการข้อผิดพลาดอย่างเป็นระบบและสอดคล้องกัน
- แยกประเภทข้อผิดพลาดตามสาเหตุและแนวทางแก้ไข
- แจ้งผู้ใช้ด้วยข้อความที่เข้าใจง่ายและเหมาะสมกับสถานการณ์
- บันทึกข้อมูลสำหรับวิเคราะห์ปัญหาเท่าที่จำเป็น
- ห้ามละเลยข้อผิดพลาดโดยไม่มีการจัดการอย่างเหมาะสม
- ห้ามใช้ข้อความแจ้งว่าสำเร็จเพื่อกลบความล้มเหลว
- หากระบบไม่สามารถยืนยันผลได้ ต้องแสดงสถานะที่ตรงกับข้อเท็จจริง

## 10. การจัดการ Dependency และการตั้งค่า (Dependency Management & Configuration)

- เลือกใช้ Library หรือ Package ที่เหมาะสม น่าเชื่อถือ และรองรับเทคโนโลยีของโปรเจกต์
- ตรวจสอบความเข้ากันได้และความเสี่ยงก่อนเพิ่มหรือเปลี่ยน Dependency
- หลีกเลี่ยงการเพิ่ม Dependency เมื่อเครื่องมือที่มีอยู่สามารถทำงานได้อย่างเหมาะสม
- แยกการตั้งค่าออกจาก Source Code ตามความเหมาะสม
- แยกค่าตั้งค่าตาม Environment เช่น Development, Testing และ Production
- ห้ามนำค่าตั้งค่าหรือข้อมูลลับจาก Environment หนึ่งไปใช้ในอีก Environment โดยไม่ตรวจสอบ
- ประเมินผลกระทบและทดสอบส่วนที่เกี่ยวข้องก่อนอัปเกรด Dependency

## 11. การทดสอบและประกันคุณภาพ (Testing & Quality Assurance)

- เลือกประเภทและระดับการทดสอบให้เหมาะสมกับความเสี่ยงของฟีเจอร์
- ทดสอบตรรกะทางธุรกิจ การตรวจสอบข้อมูล และการจัดการสถานะตามความเหมาะสม
- ทดสอบการทำงานร่วมกับระบบภายนอกและกรณีที่เกิดข้อผิดพลาด
- ทดสอบกรณีปกติ กรณีขอบเขต และกรณีข้อมูลไม่ถูกต้องที่มีนัยสำคัญ
- ทดสอบกระบวนการสำคัญตั้งแต่ต้นจนจบเมื่อจำเป็น
- ตรวจสอบว่าโค้ดใหม่ไม่ทำให้ฟังก์ชันเดิมเสียหาย
- ใช้การทดสอบอัตโนมัติร่วมกับการตรวจสอบรูปแบบอื่นตามความเหมาะสม
- ห้ามอ้างว่าการทดสอบผ่าน หากยังไม่ได้ดำเนินการและตรวจสอบผลจริง
- หากไม่สามารถทดสอบได้ ต้องระบุข้อจำกัดอย่างชัดเจน

## 12. การบำรุงรักษาและการเปลี่ยนแปลงระบบ (Maintenance & System Evolution)

- ออกแบบโค้ดให้รองรับการแก้ไขและขยายฟังก์ชันในอนาคต
- ลดการพึ่งพาระหว่างโมดูลที่ไม่จำเป็น
- ปรับปรุงโค้ดที่ซ้ำซ้อนหรือซับซ้อนเมื่อมีเหตุผลรองรับ
- ไม่ทำ Refactor ขนาดใหญ่เป็นส่วนหนึ่งของงานเล็กโดยไม่จำเป็น
- ปรับปรุงเอกสารเมื่อมีการเปลี่ยนแปลงที่ส่งผลต่อการใช้งานหรือการดูแลรักษา
- การเปลี่ยนแปลง Interface, API Contract หรือข้อมูลเดิม ต้องพิจารณาความเข้ากันได้
- รายงานปัญหาที่อยู่นอกขอบเขตงานแยกจากการแก้ไขหลัก เว้นแต่มีความจำเป็นเร่งด่วนด้านความปลอดภัยหรือความถูกต้อง

## 13. ข้อกำหนดสำหรับ AI Coding Agent (Directives & Constraints for AI Agents)

ก่อนเริ่มงาน AI ต้อง:
1. ตรวจสอบโครงสร้างโปรเจกต์และไฟล์ที่เกี่ยวข้อง
2. อ่านข้อกำหนดและเอกสารที่เป็นแหล่งอ้างอิงของงาน
3. ตรวจสอบ Tech Stack ที่กำหนดไว้ในโปรเจกต์
4. ระบุขอบเขตของการเปลี่ยนแปลงและผลกระทบที่คาดว่าจะเกิดขึ้น
5. เลือกวิธีดำเนินการที่เหมาะสมและไม่ซับซ้อนเกินจำเป็น
6. รักษาฟังก์ชันเดิมที่ไม่เกี่ยวข้องกับงาน
7. เพิ่มการจัดการข้อผิดพลาดและการทดสอบตามความเหมาะสม
8. ตรวจสอบผลลัพธ์ก่อนรายงานว่างานเสร็จสมบูรณ์
9. ใช้ภาษาไทยเป็นหลักในการสื่อสารและรายงานผล โดยคงชื่อทางเทคนิคตามต้นฉบับ
10. รายงานไฟล์ที่เปลี่ยนแปลง เหตุผลทางเทคนิค ผลการตรวจสอบ และข้อจำกัดที่ยังเหลือ

AI ต้องไม่:
- แต่งข้อกำหนดหรือข้อมูลทางเทคนิคที่ไม่มีหลักฐานรองรับ
- ทำการจำลองข้อมูลขึ้นเองโดยพลการ ให้ใช้ข้อมูลจาก API เป็นหลัก หากไม่พบหรือไม่แน่ใจให้หยุดและสอบถาม
- เปลี่ยนเทคโนโลยีหรือสถาปัตยกรรมหลักโดยไม่มีเหตุผลและการประเมินผลกระทบ
- เพิ่ม Dependency หรือเปลี่ยน Tech Stack โดยพลการ
- ลบฟังก์ชัน การทดสอบ หรือเอกสารเดิมโดยไม่มีเหตุผลรองรับ
- ปกปิดข้อผิดพลาดหรืออ้างผลการทดสอบที่ไม่ได้เกิดขึ้นจริง
- เปลี่ยนแปลงส่วนที่ไม่เกี่ยวข้องเพียงเพื่อให้โค้ดเป็นไปตามความชอบส่วนตัว

เมื่อข้อกำหนดไม่ชัดเจน AI ต้องระบุสมมติฐานให้ชัดเจน และขอคำยืนยันเมื่อสมมติฐานนั้นส่งผลต่อความถูกต้อง ความปลอดภัย ข้อมูลสำคัญ หรือขอบเขตงานอย่างมีนัยสำคัญ

หากยังไม่ได้กำหนดเทคโนโลยีที่จำเป็นต่อการดำเนินงาน AI ต้องตรวจสอบโปรเจกต์เดิมและเสนอทางเลือกพร้อมเหตุผลก่อนเลือกใช้เทคโนโลยีใหม่ที่มีผลกระทบต่อโครงสร้างระบบ

### ข้อกำหนดการดำเนินงานด้วย /speckit-implement:
- เมื่อใช้คำสั่ง `/speckit-implement` ให้ดำเนินการทีละ Phase ตามลำดับ และอนุญาตให้ดำเนินการหลาย Phase พร้อมกันได้หากมีความจำเป็น
- เมื่อดำเนินการในแต่ละ Phase แล้วเสร็จ ให้ทำ Git Commit โดยระบุรายละเอียดสิ่งที่เพิ่มหรือปรับแก้เป็นภาษาไทยอย่างชัดเจน แล้วค่อยดำเนินการใน Phase ถัดไป

## 15. เกณฑ์การส่งมอบงาน (Definition of Done & Delivery Criteria)

งานจะถือว่าเสร็จสมบูรณ์เมื่อ:
- ผลลัพธ์ตรงตามข้อกำหนดที่เกี่ยวข้อง
- โค้ดสอดคล้องกับสถาปัตยกรรมและมาตรฐานของโปรเจกต์
- จัดการข้อมูล สถานะ และข้อผิดพลาดได้เหมาะสม
- ปฏิบัติตามข้อกำหนดด้านความปลอดภัยและความเป็นส่วนตัว
- ผ่านการตรวจสอบและการทดสอบที่เกี่ยวข้อง หรือมีการระบุข้อจำกัดที่ยังเหลืออย่างชัดเจน
- ไม่มีความเสียหายต่อฟังก์ชันเดิมที่เกิดจากการเปลี่ยนแปลงโดยไม่ตั้งใจ
- มีการปรับปรุงเอกสารเมื่อจำเป็น
- มีรายงานสรุปการเปลี่ยนแปลง ผลการตรวจสอบ และประเด็นที่ยังต้องดำเนินการ
- การสื่อสารและรายงานผลใช้ภาษาไทยเป็นหลัก โดยคงชื่อทางเทคนิคให้ตรงกับระบบจริง

## 16. การบังคับใช้และข้อยกเว้น (Governance, Enforcement & Exceptions)

ธรรมนูญนี้มีผลบังคับใช้เป็นหลักการกลางสูงสุดสำหรับการพัฒนา แก้ไข ทดสอบ และบำรุงรักษาระบบส่วนหน้าบ้านทุกประเภทของโปรเจกต์

- **ลำดับความสำคัญ**: ธรรมนูญนี้มีผลผูกพันเหนือแนวปฏิบัติทั่วไป ข้อกำหนดเฉพาะของแต่ละโปรเจกต์ เช่น ภาษาโปรแกรม Framework สถาปัตยกรรม รูปแบบการจัดการสถานะ ระบบออกแบบ และข้อจำกัดทางธุรกิจ ให้กำหนดไว้ในส่วน Tech Stack และเอกสารข้อกำหนดของโปรเจกต์เพิ่มเติม
- **การจัดการความขัดแย้ง**: หากข้อกำหนดเฉพาะขัดแย้งกับธรรมนูญนี้ ต้องระบุความขัดแย้ง ประเมินผลกระทบ และเลือกแนวทางที่ถูกต้องตามข้อกำหนดที่มีอำนาจเหนือกว่า โดยไม่ละเมิดข้อกำหนดด้านความปลอดภัยหรือความถูกต้องของข้อมูล
- **ข้อยกเว้น**: ข้อยกเว้นจากหลักการของธรรมนูญต้องมีเหตุผลชัดเจน และต้องบันทึกไว้เมื่อส่งผลกระทบต่อความปลอดภัย ความถูกต้องของข้อมูล สถาปัตยกรรม หรือการบำรุงรักษาในระยะยาว
- **ขั้นตอนการแก้ไขธรรมนูญ (Amendment Procedure)**: การแก้ไขธรรมนูญต้องระบุเหตุผล ผลกระทบต่อโค้ดเดิม และได้รับการเห็นชอบก่อนนำมาบังคับใช้
- **นโยบายเลขเวอร์ชัน (Versioning Policy)**:
  - MAJOR: มีการเปลี่ยนแปลงกฎเกณฑ์หรือหลักการที่กระทบต่อแนวทางเดิมอย่างมีนัยสำคัญ
  - MINOR: มีการเพิ่มหมวดหมู่หรือขยายแนวทางปฏิบัติใหม่
  - PATCH: แก้ไขคำผิด ปรับปรุงถ้อยคำ หรือชี้แจงรายละเอียดโดยไม่เปลี่ยนหลักการเดิม
