# Feature Specification: ระบบจัดการคลังและสต็อกสินค้า (Inventory & Stock Management)

**Feature Branch**: `016-inventory-stock-management`

**Created**: 2026-10-27

**Status**: Draft

**Input**: User description: "สร้างส่วนคลังและสต๊อกสินค้าตาม api"

## Context & Background

ระบบ ice-pos-web มีเมนูการนำทางหลักสำหรับ "คลังและสต็อกสินค้า" (URL: `/inventory`) กำหนดไว้ในระบบแล้ว แต่ยังไม่มีหน้าจอการทำงานจริง ขณะเดียวกันฝั่ง Backend API มีบริการสำหรับโมดูลคลังสินค้าสมบูรณ์แล้วในกลุ่ม `05. คลังและสต็อกสินค้า` (ได้แก่ การดูสต็อกคงเหลือ, การปรับยอดสต็อกประเภทต่างๆ และการโอนย้ายสินค้าระหว่างสาขา) ฟีเจอร์นี้จึงเป็นการสร้างหน้าจอและโฟลว์การทำงานฝั่ง Web Frontend ให้เชื่อมต่อกับ API เหล่านี้อย่างครบวงจร ใช้งานง่าย และสอดคล้องกับธรรมนูญการออกแบบของระบบ

## Clarifications

### Session 2026-10-27

- Q: ขอบเขตของโมดูลคลังสินค้าในระยะแรก ควรครอบคลุมฟังก์ชันการโอนย้ายสินค้าระหว่างสาขาด้วยหรือไม่? → A: ตัวเลือก A: มุ่งเน้นการดูสต็อกคงเหลือและการปรับยอดสต็อกสินค้าทุกประเภท (IN, OUT, AUDIT, DAMAGE, EXPIRED) ให้สมบูรณ์และใช้งานได้จริงเป็นหลัก ส่วนการโอนย้ายสินค้าระหว่างสาขาตัดออกจากขอบเขตระยะแรกและรอพัฒนาในระยะถัดไปเมื่อมี API รายการใบโอนย้ายสินค้าพร้อม
- Q: ในหน้าต่างปรับยอดสต็อกประเภทตรวจนับ (AUDIT) ผู้ใช้ควรป้อนข้อมูลในรูปแบบใด? → A: ตัวเลือก A: ให้ผู้ใช้กรอก "จำนวนที่นับได้จริง (Physical Count)" แล้วระบบจะเปรียบเทียบกับยอดสต็อกปัจจุบันในระบบและคำนวณผลต่าง (Delta +/-) แสดงให้เห็นโดยอัตโนมัติก่อนกดยืนยันบันทึก
- Q: การแสดงผลและเลือกดูสต็อกสินค้าตามสาขา ควรออกแบบอย่างไรสำหรับผู้ใช้ที่มีสิทธิ์เข้าถึงหลายสาขา (เช่น ผู้ดูแลระบบ ADMIN)? → A: ตัวเลือก A: มี Dropdown ตัวเลือกสาขาที่แถบเครื่องมือด้านบน โดยค่าเริ่มต้นเป็นสาขาปัจจุบันของผู้ใช้ และอนุญาตให้ผู้ดูแลระบบสลับเลือกดูคลังสินค้าของสาขาอื่นได้ทันทีโดยไม่ต้องล็อกเอาต์
- Q: ช่องค้นหาสินค้าในหน้ารายการสต็อก ควรมีปุ่มสแกนบาร์โค้ดด้วยกล้อง (Camera Barcode Scan) ควบคู่กับการพิมพ์ค้นหาด้วยหรือไม่? → A: ตัวเลือก A: มีปุ่มสแกนบาร์โค้ดด้วยกล้องข้างช่องค้นหา (ใช้ซ้ำ `BarcodeCaptureModal` ที่มีอยู่แล้ว) เพื่อให้ผู้ใช้สามารถใช้แท็บเล็ต/มือถือส่องบาร์โค้ดเพื่อค้นหาสินค้าในคลังได้ทันที

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ดูภาพรวมและรายการสต็อกสินค้าคงเหลือรายสาขา (Priority: P1) 🎯 MVP

ในฐานะผู้จัดการร้านหรือผู้ดูแลระบบ ฉันต้องการดูรายการสต็อกสินค้าคงเหลือทั้งหมดของสาขา พร้อมตัวกรองค้นหา (ทั้งพิมพ์มือและเปิดกล้องสแกนบาร์โค้ด) ตัวเลือกสลับสาขา และตัวบ่งชี้สถานะสต็อกใกล้หมด เพื่อให้ทราบปริมาณสินค้าพร้อมขายและวางแผนสั่งซื้อหรือเติมสินค้าได้อย่างทันท่วงที

**Why this priority**: เป็นหัวใจสำคัญอันดับแรก (Core Visibility) ของระบบสต็อก หากไม่มีการแสดงยอดสต็อก ผู้ใช้จะไม่สามารถตรวจสอบสถานะคลังหรือดำเนินการอื่นต่อได้ เป็นชิ้นงาน MVP ที่พร้อมส่งมอบประโยชน์ได้ทันที

**Independent Test**: สามารถเปิดหน้า `/inventory` ดูตารางยอดสต็อกสินค้า กรองสินค้าใกล้หมด (Low Stock) ใช้ปุ่มกล้องสแกนบาร์โค้ดเพื่อค้นหา และสลับดูสต็อกสาขาอื่นได้ถูกต้องตาม API

**Acceptance Scenarios**:

1. **Given** ผู้ใช้เข้าสู่ระบบด้วยสิทธิ์ ADMIN หรือ MANAGER และเปิดหน้า `/inventory`  
   **When** หน้าจอโหลดเสร็จสมบูรณ์  
   **Then** แสดงตารางรายการสต็อกของสาขาปัจจุบัน พร้อมการ์ดสรุปภาพรวม (จำนวนรายการทั้งหมด, รายการสต็อกต่ำ, รายการสินค้าหมดสต็อก)
2. **Given** รายการสต็อกกำลังแสดงผลอยู่  
   **When** ผู้ใช้กดเลือกตัวกรอง "เฉพาะสต็อกต่ำกว่าเกณฑ์" (Low Stock Only)  
   **Then** ตารางจะแสดงเฉพาะสินค้าที่มีจำนวนคงเหลือน้อยกว่าหรือเท่ากับเกณฑ์ขั้นต่ำ (`minStock`)
3. **Given** มีสินค้าหลายรายการ  
   **When** ผู้ใช้พิมพ์ค้นหาด้วยชื่อสินค้า / รหัส SKU หรือกดปุ่มไอคอนกล้องเพื่อสแกนบาร์โค้ดด้วยกล้อง  
   **Then** ตารางจะกรองและแสดงเฉพาะรายการสินค้าที่ตรงกับรหัสบาร์โค้ดหรือคำค้นหานั้นทันที
4. **Given** ผู้ใช้เป็น ADMIN ที่มีสิทธิ์ดูแลหลายสาขา  
   **When** ผู้ใช้เลือกสาขาอื่นจาก Dropdown ที่แถบเครื่องมือด้านบน  
   **Then** ระบบโหลดและแสดงข้อมูลสต็อกสินค้าคงเหลือของสาขาที่เลือกใหม่ทันที

---

### User Story 2 - ปรับยอดสต็อกสินค้าตามประเภทเหตุการณ์ (Priority: P2)

ในฐานะผู้จัดการสาขา ฉันต้องการบันทึกการปรับยอดสต็อกสินค้า (เช่น รับของเข้า `IN`, นำของออก `OUT`, ตรวจนับสต็อกตามจริง `AUDIT`, ตัดสินค้าชำรุด `DAMAGE` หรือตัดสินค้าหมดอายุ `EXPIRED`) พร้อมระบุเหตุผล เพื่อให้ยอดสินค้าคงเหลือในระบบตรงกับความเป็นจริงและมีประวัติการปรับยอดที่ตรวจสอบได้

**Why this priority**: การขายและการจัดการคลังจริงมักพบสินค้าชำรุด สูญหาย หรือนับยอดคลาดเคลื่อน ฟังก์ชันปรับยอดสต็อกเป็นเครื่องมือจำเป็นในการควบคุมความถูกต้องของคลังสินค้า

**Independent Test**: เลือกสินค้า 1 ชิ้น กดปุ่ม "ปรับยอดสต็อก" เลือกประเภทเหตุการณ์ (เช่น AUDIT หรือ DAMAGE) ระบุจำนวนและเหตุผล บันทึกสำเร็จ ยอดในตารางจะอัปเดตทันที

**Acceptance Scenarios**:

1. **Given** ผู้ใช้อยู่ที่หน้ารายการสต็อกสินค้า  
   **When** ผู้ใช้กดปุ่ม "ปรับยอดสต็อก" บนรายการสินค้าที่ต้องการ  
   **Then** หน้าต่าง Modal ปรับยอดสต็อกเปิดขึ้น แสดงชื่อสินค้า, สาขา, ยอดสต็อกปัจจุบัน และมีตัวเลือกประเภทการปรับยอด (IN, OUT, AUDIT, DAMAGE, EXPIRED)
2. **Given** ผู้ใช้เลือกประเภท "ตรวจนับสต็อก" (AUDIT)  
   **When** ผู้ใช้ระบุ "จำนวนที่นับได้จริง (Physical Count)"  
   **Then** ระบบคำนวณและแสดงผลต่าง (Delta +/-) เทียบกับสต็อกเดิมให้เห็นอัตโนมัติก่อนกดยืนยันบันทึก
3. **Given** ผู้ใช้กำลังปรับยอดยกออก (OUT หรือ DAMAGE)  
   **When** ระบุจำนวนที่ทำให้ยอดคงเหลือติดลบ  
   **Then** ระบบแจ้งเตือนข้อผิดพลาดภาษาไทยและไม่อนุญาตให้ส่งคำขอที่ทำให้สต็อกติดลบ

---

### User Story 3 - ดูสรุปมูลค่าสต็อกสินค้าคงเหลือ (Priority: P3)

ในฐานะเจ้าของร้านหรือผู้ดูแลระบบ ฉันต้องการดูสรุปมูลค่ารวมของสินค้าคงคลังตามราคาต้นทุน เพื่อใช้ประเมินมูลค่าทรัพย์สินหมุนเวียนในคลังของแต่ละสาขา

**Why this priority**: ให้ข้อมูลเชิงลึกด้านการเงินและการบริหารจัดการคลังสินค้า เสริมการทำงานของฝ่ายบัญชีและบริหาร

**Independent Test**: เปิดการ์ดสรุปหรือแท็บ "มูลค่าสินค้าคงคลัง" ข้อมูลมูลค่าต้นทุนรวมจะถูกคำนวณและแสดงผลอย่างถูกต้อง

**Acceptance Scenarios**:

1. **Given** ผู้ใช้อยู่ในหน้าระบบคลังสินค้า  
   **When** ดูการ์ดสรุปมูลค่าสินค้าคงคลัง  
   **Then** แสดงยอดมูลค่ารวมเป็นสกุลเงินบาท (คำนวณจากยอดสต็อกคงเหลือ x ต้นทุนต่อหน่วย) ตรงตามรายงานสรุป

---

### Out of Scope (ขอบเขตที่ยกไปพัฒนาในระยะถัดไป)

- **การโอนย้ายสินค้าระหว่างสาขา (Stock Transfer)**: รอจนกว่าจะมี Backend API สำหรับดึงรายการประวัติใบโอนย้ายสินค้า (`GET /inventory/transfers`) อย่างสมบูรณ์

---

### Edge Cases

- **สาขาไม่มีสินค้าคงคลังเลย**: แสดง Empty State ภาษาไทยอย่างชัดเจน พร้อมปุ่มแนะนำให้ไปเพิ่มสินค้าใน Catalog หรือรับสต็อกเข้า
- **สัญญาณอินเทอร์เน็ตขาดหายขณะกดปรับสต็อก**: แสดง Error Dialog ภาษาไทย พร้อมป้องกันการส่งคำขอซ้ำด้วย Idempotency Key
- **การปรับยอดสต็อกพร้อมกัน (Concurrent Adjustment)**: หากยอดสต็อกหรือ Version มีการเปลี่ยนแปลงจากเครื่องอื่น ให้แจ้งเตือนและให้รีเฟรชข้อมูลล่าสุด
- **สินค้าขายตามน้ำหนัก (Weight-based)**: ช่องระบุจำนวนในการปรับยอดสต็อกต้องรองรับทศนิยมอย่างถูกต้อง
- **สิทธิ์การเข้าถึง**: ผู้ใช้ระดับ CASHIER ที่พยายามเข้าหน้า `/inventory` จะต้องถูกปฏิเสธหรือส่งกลับหน้า `/pos`

---

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: ระบบ MUST จัดเตรียมเส้นทางหน้าเว็บ `/inventory` ภายใต้ Layout หลัก พร้อมจำกัดสิทธิ์เฉพาะผู้ใช้บทบาท `ADMIN` และ `MANAGER`
- **FR-002**: ระบบ MUST ดึงข้อมูลระดับสต็อกสินค้าคงเหลือจาก API `GET /api/v1/inventory/stocks` ตามสาขาที่เลือก และมี Dropdown สลับสาขาที่แถบเครื่องมือด้านบน
- **FR-003**: ระบบ MUST แสดงตัวกรอง "เฉพาะสต็อกต่ำกว่าเกณฑ์" (`lowStockOnly`) และรองรับ Pagination เมื่อมีสินค้าจำนวนมาก
- **FR-004**: ระบบ MUST มีช่องค้นหาสินค้าด่วนด้วยชื่อสินค้า รหัส SKU หรือรหัสบาร์โค้ด พร้อมปุ่มเปิดกล้องสแกนบาร์โค้ด (ใช้ซ้ำ `BarcodeCaptureModal`)
- **FR-005**: ระบบ MUST แสดงการ์ดสรุปสถานะสต็อกภาพรวมด้านบน (จำนวนรายการสินค้าทั้งหมด, รายการสินค้าสต็อกต่ำ, รายการสินค้าหมด)
- **FR-006**: ระบบ MUST มีฟังก์ชัน "ปรับยอดสต็อกสินค้า" ผ่าน API `POST /api/v1/inventory/adjust` รองรับประเภท: รับเข้า (`IN`), ปรับออก (`OUT`), ตรวจนับสต็อก (`AUDIT`), สินค้าชำรุดเสียหาย (`DAMAGE`), สินค้าหมดอายุ (`EXPIRED`)
- **FR-007**: ในกรณีประเภทตรวจนับสต็อก (`AUDIT`) ระบบ MUST ให้ผู้ใช้ระบุจำนวนที่นับได้จริง (Physical Count) และคำนวณผลต่าง (Delta +/-) แสดงให้เห็นอัตโนมัติก่อนส่งคำขอ
- **FR-008**: ระบบ MUST บังคับให้ระบุเหตุผล (Reason) ทุกครั้งที่มีการปรับยอดสต็อก และมีระบบป้องกันสต็อกติดลบ
- **FR-009**: ระบบ MUST สร้าง UUID สำหรับ `idempotencyKey` ในทุกการส่งคำขอปรับยอดสต็อก เพื่อป้องกันการหัก/เพิ่มซ้ำซ้อน
- **FR-010**: ระบบ MUST มี Loading Overlay ป้องกันการกดซ้ำขณะเรียกใช้งาน API ตามข้อกำหนดธรรมนูญข้อ 6.6
- **FR-011**: องค์ประกอบการสัมผัส (Buttons, Selects, Inputs) ต้องมีขนาดอย่างน้อย 48x48px ตามข้อกำหนดธรรมนูญข้อ 6.5 (Elderly-Friendly)
- **FR-012**: ข้อความบนหน้าจอ ป้ายสถานะ และกล่องแจ้งเตือนต้องใช้ภาษาไทยที่กระชับ ชัดเจน ตามธรรมนูญข้อ 2.1

### Key Entities *(include if feature involves data)*

- **StockLevel**: ข้อมูลระดับสต็อกสินค้าคงเหลือรายสาขา ประกอบด้วย รหัสสต็อก (`id`), รหัสสินค้า (`productId`), รหัสสาขา (`branchId`), ปริมาณคงเหลือจริง (`quantity`), ปริมาณที่ถูกจอง (`reservedQuantity`), ข้อมูลสินค้า (`product`), เวลาอัปเดตล่าสุด (`updatedAt`)
- **StockAdjustment**: การทำรายการปรับยอดสต็อก ประกอบด้วย รหัสสาขา (`branchId`), รหัสสินค้า (`productId`), ประเภทการปรับ (`type`), จำนวนเปลี่ยนแปลงหรือจำนวนนับได้ (`quantityDelta`), เหตุผล (`reason`), คีย์ป้องกันการทำซ้ำ (`idempotencyKey`)
- **StockTransfer**: ใบโอนย้ายสินค้าระหว่างสาขา ประกอบด้วย เลขที่ใบโอน (`transferNo`), สาขาต้นทาง (`fromBranchId`), สาขาปลายทาง (`toBranchId`), สถานะ (`status`: PENDING, COMPLETED, CANCELLED), รายการสินค้าที่โอน (`lines`: productId, quantity, uomId), วันที่สร้าง (`createdAt`), วันที่รับ (`receivedAt`)

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ผู้จัดการร้านสามารถตรวจสอบสถานะและยอดคงเหลือของสินค้าในคลังได้ภายใน 2 วินาทีหลังจากเปิดหน้าจอ
- **SC-002**: ผู้ใช้สามารถทำรายการปรับยอดสต็อกสินค้า (ตรวจนับ/ตัดชำรุด) ได้เสร็จสิ้นภายในไม่เกิน 3 ขั้นตอน
- **SC-003**: ข้อมูลสต็อกคงเหลือบนหน้าจอตรงกับข้อมูลจริงในระบบ Backend API 100% โดยไม่มีการจำลองข้อมูลขึ้นเอง
- **SC-004**: ระบบแสดง Loading Overlay บล็อกการคลิกซ้ำได้ 100% ในทุกการกระทำที่ส่งคำขอไปยัง API ปรับยอดหรือโอนย้าย

## Assumptions

- ข้อมูลสาขา (Branches) ดึงมาจากบริบทการเข้าสู่ระบบของผู้ใช้หรือบริการสาขาที่มีอยู่เดิม

- การควบคุมสิทธิ์เบื้องต้นกระทำผ่าน Route Protection และ Role Verification ของระบบเดิม
- สำหรับการแสดงผลสต็อกใน POS เดิม (`src/utils/posStockHelper.ts`) จะยังคงทำงานร่วมกับข้อมูลสต็อกนี้ได้อย่างราบรื่น
