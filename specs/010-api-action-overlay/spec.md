# Feature Specification: ระบบแสดง Loading Overlay บล็อกการทำงานขณะมี Action เรียกใช้งาน API (API Action Loading Overlay & Interaction Blocking)

**Feature Branch**: `010-api-action-overlay`

**Created**: 2026-10-25

**Status**: Draft

**Input**: User description: "ตรวจสอบและปรับแก้ระบบให้ตรงกับธรรมนูญใหม่ (เพิ่ม overlay หากมีการกระทำ action ใดๆ ที่มีความเกี่ยวข้องกับ api แสดงจนกว่าจะดำเนินการแล้วเสร็จ ตามธรรมนูญ v1.5.0 ข้อ 6.6)"

## Clarifications

### Session 2026-10-25

- Q: ควรยกเว้นคำขอ API ประเภทงานเบื้องหลังแบบเงียบ (Silent Background Tasks เช่น Silent Token Refresh) จากการแสดง Full-Screen Blocking Overlay หรือไม่? → A: ยกเว้นงานเบื้องหลังแบบเงียบ (Silent Tasks เช่น Silent Token Refresh) โดยบล็อกหน้าจอเฉพาะ User-Triggered Actions เพื่อไม่ให้รบกวนการขายของแคชเชียร์
- Q: ระยะเวลา Timeout สูงสุดของการแสดง Overlay เมื่อ API ค้างหรือไม่ตอบสนอง ควรตั้งไว้เท่าใดก่อนจะตัดการทำงาน (Auto-Dismiss) และแจ้งเตือนข้อผิดพลาด? → A: 15 วินาที สำหรับคำขอทั่วไป และ 30 วินาที สำหรับธุรกรรมชำระเงิน/ออกบิล ก่อน Auto-Dismiss และแจ้งเตือนข้อผิดพลาด

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Transaction & Form Submission Blocking Overlay (Priority: P1) 🎯 MVP

เมื่อผู้ใช้งานหรือแคชเชียร์กดปุ่มกระทำการสำคัญที่ต้องส่งข้อมูลผ่าน API (เช่น ยืนยันการขาย, ชำระเงิน, บันทึกฟอร์ม, ลบรายการสินค้า, เข้าสู่ระบบ, ยกเลิกบิล) ระบบต้องแสดง Loading Overlay คลุมทับหน้าจอทันที พร้อมฉากกั้น (Backdrop) เพื่อบล็อกการคลิกหรือสัมผัสซ้ำ และแสดงข้อความสถานะภาษาไทยชัดเจน จนกว่าการดำเนินการจะเสร็จสิ้นสมบูรณ์

**Why this priority**: เป็นหัวใจหลักของข้อกำหนดในธรรมนูญ v1.5.0 ข้อ 6.6 เพื่อป้องกันความผิดพลาดขั้นวิกฤต เช่น การกดชำระเงินหรือส่งข้อมูลซ้ำซ้อน (Double Submit / Duplicate Payment) ระหว่างที่ระบบกำลังประมวลผล

**Independent Test**: สามารถทดสอบได้อย่างสมบูรณ์โดยการกดปุ่มชำระเงินหรือปุ่มบันทึกข้อมูล แล้วทดลองคลิกปุ่มซ้ำหรือกดส่วนอื่นของหน้าจอ ตรวจสอบว่าระบบบล็อกการกดทั้งหมด แสดง Backdrop และข้อความโหลด และปลดล็อกเมื่อการทำรายการสำเร็จหรือล้มเหลว

**Acceptance Scenarios**:

1. **Given** แคชเชียร์อยู่ที่หน้าจอชำระเงินหรือฟอร์มทำรายการ, **When** แคชเชียร์กดปุ่ม "ยืนยันชำระเงิน" หรือปุ่มบันทึก, **Then** ระบบต้องแสดง Loading Overlay พร้อม Backdrop ทึบแสงบางส่วนคลุมหน้าจอ และแสดงตัวหมุนโหลด (Spinner) พร้อมข้อความภาษาไทย เช่น "กำลังประมวลผลการชำระเงิน กรุณารอสักครู่..." โดยบล็อกการคลิกปุ่มทุกชนิด
2. **Given** กำลังแสดง Loading Overlay ระหว่างเรียก API, **When** API ส่งผลตอบกลับสำเร็จ (HTTP 200/201 OK) และหน้าบ้านอัปเดตสถานะเสร็จสิ้น, **Then** Loading Overlay ต้องปิดลงทันที และแสดงผลหน้าจอขั้นตอนถัดไปอย่างราบรื่น
3. **Given** กำลังแสดง Loading Overlay ระหว่างเรียก API, **When** API ตอบกลับด้วยสถานะข้อผิดพลาด (เช่น 400, 422, 500) หรือการเชื่อมต่อเครือข่ายขัดข้อง, **Then** Loading Overlay ต้องปิดลงทันที และแสดงกล่องแจ้งเตือนข้อผิดพลาด (Error Dialog / Notification) ภาษาไทยที่ชัดเจน เพื่อให้ผู้ใช้สามารถตรวจสอบและทำรายการใหม่ได้ โดยหน้าจอไม่ค้าง

### User Story 2 - Data Query & Navigation Action Overlay (Priority: P2)

เมื่อผู้ใช้สั่งการให้ค้นหาข้อมูล โหลดข้อมูลสินค้า โหลดข้อมูลสาขา หรือเปลี่ยนหน้าจอที่มีการเรียก API ระบบต้องแสดงสถานะการโหลดและควบคุมการปฏิสัมพันธ์ของผู้ใช้ เพื่อไม่ให้เกิดภาวะข้อมูลสับสน (Race Condition) หรือการกดย้ำ

**Why this priority**: เพิ่มความราบรื่นในการใช้งานและสอดคล้องกับมาตรฐาน Elderly-Friendly Design เพื่อให้ผู้ใช้ทุกวัยรับทราบว่าระบบกำลังดึงข้อมูลอยู่จริง

**Independent Test**: ทำการค้นหาสินค้าหรือเลือกเปลี่ยนหมวดหมู่สินค้า ตรวจสอบว่ามีสถานะการโหลดบอกความคืบหน้าชัดเจนและป้องกันการกดสลับหมวดหมู่รัวๆ

**Acceptance Scenarios**:

1. **Given** แคชเชียร์อยู่ที่หน้าจอขาย POS, **When** แคชเชียร์ค้นหาสินค้าหรือเลือกเปลี่ยนหมวดหมู่ที่มีการดึงข้อมูลจาก API, **Then** ระบบต้องแสดง Indicator / Overlay บอกสถานะ "กำลังโหลดข้อมูลสินค้า..." และควบคุมไม่ให้กดซ้ำจนกว่าข้อมูลจะแสดงผลเสร็จสมบูรณ์

### User Story 3 - Silent Background Requests Differentiation (Priority: P3)

ระบบต้องสามารถแยกแยะระหว่าง "การกระทำของผู้ใช้ (User-Triggered Action)" ที่ต้องแสดง Full Blocking Overlay กับ "งานประมวลผลเบื้องหลังแบบเงียบ (Silent Background Task)" เช่น การต่ออายุโทเค็นอัตโนมัติ (Silent Token Refresh) หรือการตรวจสอบสถานะระบบเบื้องหลัง เพื่อไม่ให้รบกวนหรือขัดจังหวะการทำงานต่อเนื่องของแคชเชียร์

**Why this priority**: ป้องกันปัญหาหน้าจอติดขัด (UI Stutter / Interruption) โดยไม่จำเป็นขณะที่แคชเชียร์กำลังเลือกสินค้าหรือป้อนตัวเลข

**Independent Test**: ขณะที่แคชเชียร์กำลังเลือกดูรายการสินค้า ให้จำลองการทำงานของ Silent Token Refresh เบื้องหลัง ตรวจสอบว่าแคชเชียร์ยังคงสามารถเลือกสินค้าและใช้งานหน้าจอได้ตามปกติ โดยไม่มี Full Blocking Overlay มาขัดจังหวะ

**Acceptance Scenarios**:

1. **Given** แคชเชียร์กำลังใช้งานหน้าจอขาย POS ตามปกติ, **When** ระบบตรวจพบโทเค็นหมดอายุและทำการส่งคำขอ Silent Refresh เบื้องหลัง, **Then** ระบบต้องไม่แสดง Full Screen Blocking Overlay ที่ขัดขวางการทำงานของผู้ใช้ และดำเนินการต่ออายุเงียบๆ ได้สำเร็จ

---

### Edge Cases

- **การเรียก API พร้อมกันหลายคำขอ (Multiple Concurrent API Requests)**: เมื่อมี Action ที่ส่งผลให้มีการเรียก API มากกว่า 1 คำขอพร้อมกัน ระบบต้องใช้กลไก Request Counter (หรือ Reference Counting) โดย Overlay จะแสดงค้างไว้จนกว่าคำขอทั้งหมดจะเสร็จสิ้น และจะปิดลงเมื่อ Counter ลดลงเหลือ 0
- **การเชื่อมต่อเครือข่ายหลุดหรือ Timeout (Network Timeout / Offline)**: หาก API ไม่ตอบกลับภายในระยะเวลาที่กำหนด (15 วินาทีสำหรับคำขอทั่วไป และ 30 วินาทีสำหรับธุรกรรมชำระเงิน/ออกบิล) ระบบต้องทำการตัดการทำงาน (Auto-Dismiss) ของ Overlay และแสดงกล่องข้อความแจ้งเตือน "การเชื่อมต่อขัดข้องหรือหมดเวลา กรุณาตรวจสอบสัญญาณอินเทอร์เน็ตและลองใหม่อีกครั้ง" พร้อมปุ่มปิดเพื่อปลดล็อกหน้าจอ
- **การกดยกเลิกในกรณีฉุกเฉิน (Emergency Escape)**: มีกลไกป้องกันการค้างถาวรด้วยการตัดการทำงานอัตโนมัติ (Auto-Dismiss) เมื่อเกินขีดจำกัดเวลาสูงสุดพร้อม Error Alert เพื่อไม่ให้หน้าจอ POS ใช้งานไม่ได้

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: ระบบต้องมี Global Action Loading Overlay ที่ประกอบด้วยฉากกั้นทึบแสงบางส่วน (Semi-transparent Backdrop) ที่ครอบคลุมหน้าจอ และตัวแสดงผลสถานะการทำงาน (Spinner / Loading Indicator)
- **FR-002**: Loading Overlay ต้องบล็อก Pointer Events (คลิก, สัมผัส, แตะ, เลื่อน) ทั้งหมด เพื่อป้องกันการกระทำซ้ำซ้อน (Duplicate Action / Rapid Clicking) ขณะที่ API กำลังประมวลผล
- **FR-003**: Loading Overlay ต้องเริ่มแสดงผลทันทีที่มีการกระทำที่เรียกใช้ API และแสดงอย่างต่อเนื่องจนกว่าคำขอดังกล่าวจะเสร็จสิ้นสมบูรณ์ (ทั้งกรณีสำเร็จหรือข้อผิดพลาด)
- **FR-004**: Loading Overlay ต้องแสดงข้อความภาษาไทยที่ชัดเจน กระชับ ตรงกับบริบทการกระทำ เช่น "กำลังประมวลผล...", "กำลังบันทึกข้อมูล...", "กำลังเชื่อมต่อระบบ กรุณารอสักครู่"
- **FR-005**: ระบบต้องรองรับการจัดการคำขอที่ทำงานพร้อมกัน (Concurrent Requests) ผ่านกลไกตัวนับ โดย Overlay จะแสดงตราบเท่าที่มีคำขอของ Action ค้างอยู่ และปิดเมื่อคำขอทั้งหมดสิ้นสุด
- **FR-006**: ระบบต้องปิด Overlay ทันทีเมื่อเกิดข้อผิดพลาด และแสดงกล่องข้อความแจ้งเตือน (Error Dialog / Notification) ภาษาไทยที่เข้าใจง่าย พร้อมปลดล็อกหน้าจอให้ผู้ใช้แก้ไขข้อมูลหรือลองใหม่ได้
- **FR-007**: ระบบต้องแยกแยะระหว่างคำขอที่เกิดจาก User Action (ต้องแสดง Blocking Overlay) และคำขอแบบ Silent Background Task (เช่น Silent Token Refresh) ที่ไม่ต้องแสดง Full Blocking Overlay
- **FR-008**: การออกแบบ Overlay และตัวอักษรต้องสอดคล้องกับมาตรฐาน Elderly-Friendly Design (ตัวอักษรขนาดใหญ่อ่านง่าย คอนทราสต์ชัดเจน WCAG 2.1 AA)
- **FR-009**: ระบบต้องมีกลไกป้องกันการค้างถาวร (Emergency Auto-Dismiss) โดยตัดการทำงานของ Overlay และแสดงข้อความแจ้งเตือนข้อผิดพลาดทันทีเมื่อคำขอเกินเวลา 15 วินาทีสำหรับคำขอทั่วไป หรือ 30 วินาทีสำหรับธุรกรรมชำระเงิน/ออกบิล

### Key Entities *(include if feature involves data)*

- **OverlayState**: ตัวแทนสถานะของ Global Loading Overlay ประกอบด้วย:
  - `isVisible`: สถานะเปิด/ปิดของ Overlay
  - `message`: ข้อความภาษาไทยที่แสดงบน Overlay
  - `activeRequestsCount`: ตัวนับจำนวนคำขอ API ที่กำลังทำงานอยู่
  - `isSilent`: ธงระบุว่าคำขอนี้เป็นการทำงานเบื้องหลังโดยไม่ต้องแสดง Overlay บล็อกหน้าจอหรือไม่

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: อัตราการเกิดคำขอซ้ำซ้อนจากการกดปุ่มรัวๆ (Duplicate API Submissions) ของผู้ใช้เป็น 0% ในทุก Action สำคัญ (การบันทึก, ชำระเงิน, ลบ)
- **SC-002**: Loading Overlay แสดงผลบนหน้าจอภายในเวลาไม่เกิน 100ms หลังเกิดการกระทำของผู้ใช้
- **SC-003**: Loading Overlay ถูกปลดออกและคืนการควบคุมหน้าจอให้ผู้ใช้ภายในไม่เกิน 100ms หลังจาก API และการอัปเดตหน้าบ้านเสร็จสิ้น
- **SC-004**: ผู้ใช้งาน 100% ได้รับข้อความภาษาไทยอธิบายสถานะที่ชัดเจนทุกครั้งที่ระบบกำลังรอผลลัพธ์จาก API โดยไม่มีหน้าจอค้างโดยไม่ทราบสาเหตุ
- **SC-005**: การต่ออายุโทเค็นอัตโนมัติ (Silent Refresh) ไม่ทำให้เกิดการกระตุกหรือแสดง Full Blocking Overlay ขัดขวางการขายของแคชเชียร์
- **SC-006**: ระบบตัดการทำงานของ Overlay และคืนการควบคุมหน้าจอให้ผู้ใช้เมื่อคำขอใช้เวลาเกินขีดจำกัด (15 วินาทีสำหรับคำขอทั่วไป และ 30 วินาทีสำหรับธุรกรรมชำระเงิน/ออกบิล) 100% ของกรณีคำขอค้าง

## Assumptions

- ระบบจัดการการเรียก API ทั้งหมดผ่าน API Client กลางใน `src/services/api.ts`
- หน้าจอ POS รองรับทั้งการสัมผัส (Touchscreen) และอุปกรณ์เมาส์/คีย์บอร์ด
- ข้อความและป้ายกำกับทั้งหมดใช้ภาษาไทยเป็นหลักตามธรรมนูญการพัฒนาระบบ
