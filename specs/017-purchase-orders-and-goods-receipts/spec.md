# Feature Specification: ระบบใบสั่งซื้อสินค้าและตรวจรับสินค้าเข้าคลัง (Purchase Orders & Goods Receipts)

**Feature Branch**: `017-purchase-orders-and-goods-receipts`

**Created**: 2026-10-27

**Status**: Draft

**Input**: User description: "เพิ่มส่วน ใบสั่งซื้อสินค้า กับ ส่วน ตรวจรับสินค้าเข้าคลัง โดยใช้ข้อมูลจาก api"

## Context & Background

ระบบ ice-pos-web ได้พัฒนาส่วนการจัดการสต็อกสินค้าคงเหลือและการปรับยอดสต็อกแล้ว (`/inventory`) แต่ยังขาดกระบวนการต้นน้ำที่สำคัญสำหรับการเติมสินค้าเข้าคลัง ได้แก่:
1. **การสั่งซื้อสินค้า (Purchase Order - PO)**: การออกเอกสารสั่งซื้อสินค้าไปยังผู้จัดจำหน่าย (Supplier) ระบุสินค้า ปริมาณ ต้นทุน และกำหนดวันส่งมอบ
2. **การตรวจรับสินค้าเข้าคลัง (Goods Receipt - GR)**: การตรวจรับสินค้าจริงเมื่อของมาส่ง ตรวจนับจำนวนรับจริง คัดแยกสินค้าชำรุดเสียหาย บันทึก Lot/วันหมดอายุ และยืนยันการนำสต็อกเข้าคลังสินค้าสาขาจริง

Backend API มี Endpoint รองรับพร้อมใช้งานในกลุ่ม `04.2 ใบสั่งซื้อสินค้า (Purchase Orders)` (8 Endpoints) และ `04.3 ตรวจรับสินค้าเข้าคลัง (Goods Receipts)` (5 Endpoints) ร่วมกับข้อมูลผู้จัดจำหน่าย `04.1 ผู้จัดจำหน่าย (Suppliers)` ฟีเจอร์นี้จึงเป็นการสร้างหน้าจอและโฟลว์การทำงานบน Web Frontend เพื่อเชื่อมต่อการทำงานของทั้งสองส่วนอย่างสมบูรณ์ ถูกต้องตามหลักธรรมนูญของระบบ

## User Scenarios & Testing *(mandatory)*

### User Story 1 - จัดการและติดตามใบสั่งซื้อสินค้า (Purchase Orders) (Priority: P1) 🎯 MVP

ในฐานะผู้จัดการสาขาหรือฝ่ายจัดซื้อ ฉันต้องการดูรายการใบสั่งซื้อ กรองสถานะและค้นหา สร้างใบสั่งซื้อใหม่ส่งไปยังผู้จัดจำหน่าย และยืนยันการสั่งซื้อ เพื่อควบคุมการจัดซื้อสินค้าอย่างเป็นระบบและมีเอกสารอ้างอิงชัดเจน

**Why this priority**: เป็นจุดเริ่มต้นของวงจรการเติมสต็อกสินค้า หากไม่มีใบสั่งซื้อ จะไม่สามารถระบุแผนการรับของหรือตรวจสอบความถูกต้องในการส่งมอบสินค้าได้

**Independent Test**: สามารถเปิดหน้ารายการใบสั่งซื้อ ดูตารางรายการ สร้างใบสั่งซื้อใหม่ระบุ Supplier และรายการสินค้า บันทึกฉบับร่าง (DRAFT) และกดยืนยันสั่งซื้อ (ORDERED) ได้สำเร็จตาม API

**Acceptance Scenarios**:

1. **Given** ผู้ใช้มีสิทธิ์ ADMIN หรือ MANAGER เข้าสู่หน้าจัดการใบสั่งซื้อ  
   **When** หน้าจอโหลดเสร็จสมบูรณ์  
   **Then** แสดงตารางรายการใบสั่งซื้อ พร้อมตัวกรองสถานะ (DRAFT, ORDERED, PARTIALLY_RECEIVED, COMPLETED, CANCELLED), ตัวกรองสาขา และช่องค้นหา
2. **Given** ผู้ใช้ต้องการสั่งซื้อสินค้าเพิ่ม  
   **When** กดปุ่ม "สร้างใบสั่งซื้อใหม่" เลือกผู้จัดจำหน่าย กำหนดวันที่ส่งมอบ และเลือกรายการสินค้าพร้อมระบุจำนวนและราคาต้นทุน  
   **Then** ระบบคำนวณยอดรวมและภาษีอย่างถูกต้อง พร้อมบันทึกเป็น DRAFT หรือสั่งซื้อทันที (ORDERED)
3. **Given** ใบสั่งซื้ออยู่ในสถานะ DRAFT  
   **When** ผู้ใช้กดแก้ไข หรือกดยืนยันการสั่งซื้อ (Confirm PO)  
   **Then** ระบบส่งคำขอยืนยันไปยัง API และเปลี่ยนสถานะเป็น ORDERED พร้อมสำหรับขั้นตอนการตรวจรับสินค้า
4. **Given** ใบสั่งซื้อที่ต้องการยกเลิก  
   **When** ผู้ใช้กดยกเลิกใบสั่งซื้อ (Cancel PO)  
   **Then** แสดงกล่องข้อความยืนยันภาษาไทย และเปลี่ยนสถานะเป็น CANCELLED ป้องกันการนำไปตรวจรับ

### User Story 2 - ตรวจรับสินค้าเข้าคลังจากใบสั่งซื้อ (Goods Receipt from PO) (Priority: P2)

ในฐานะพนักงานคลังหรือผู้จัดการสาขา เมื่อมีสินค้ามาส่ง ฉันต้องการตรวจรับสินค้าโดยดึงรายการจากใบสั่งซื้อ (Pending Items Preview) ตรวจนับจำนวนรับจริง คัดแยกสินค้าเสียหาย บันทึกเลข Lot/วันหมดอายุ และยืนยันนำสินค้าเข้าสต็อกสาขา

**Why this priority**: เป็นขั้นตอนที่มีผลต่อสต็อกสินค้าจริงในคลัง การรับสินค้าที่ถูกต้องช่วยป้องกันสินค้าขาด/เกิน และอัปเดตสต็อกพร้อมขายในระบบ POS ทันที

**Independent Test**: สามารถเลือกใบสั่งซื้อที่มีสถานะ ORDERED กดสร้างใบตรวจรับ ระบบดึงรายการค้างรับมาแสดงอัตโนมัติ ระบุจำนวนรับจริงและกดยืนยันตรวจรับเสร็จสมบูรณ์ (Complete) สต็อกในคลังของสาขาจะเพิ่มขึ้นทันที

**Acceptance Scenarios**:

1. **Given** มีใบสั่งซื้อที่ได้รับการยืนยันแล้ว (ORDERED หรือ PARTIALLY_RECEIVED)  
   **When** ผู้ใช้กด "ตรวจรับสินค้า" จากใบสั่งซื้อนั้น  
   **Then** ระบบดึงรายการสินค้าค้างรับจาก API `/api/v1/purchase-orders/{id}/receipt-preview` มาเติมในฟอร์มตรวจรับอัตโนมัติ
2. **Given** สินค้าที่มาส่งมีบางส่วนชำรุดเสียหาย  
   **When** ผู้ใช้ระบุจำนวนที่รับได้จริง (`receivedQuantity`) และจำนวนคัดทิ้ง (`rejectedQuantity`) พร้อมระบุเหตุผลคัดทิ้ง (`rejectReason`)  
   **Then** ระบบบันทึกแยกยอดรับจริงและยอดคัดทิ้งอย่างชัดเจน
3. **Given** สินค้าที่ตรวจรับเป็นสินค้ามีอายุการใช้งานหรือต้องคุมล็อต  
   **When** ผู้ใช้กรอกเลขล็อต (`lotNumber`) และวันหมดอายุ (`expiryDate`)  
   **Then** ข้อมูลถูกบันทึกแนบไปกับรายการตรวจรับ
4. **Given** ข้อมูลตรวจรับครบถ้วน  
   **When** ผู้ใช้กดยืนยันตรวจรับเข้าคลัง (Complete Goods Receipt)  
   **Then** ระบบส่งคำขอยืนยันไปยัง API สต็อกสินค้าของสาขาได้รับการอัปเดตเพิ่มขึ้นจริง และสถานะใบสั่งซื้อเปลี่ยนเป็น PARTIALLY_RECEIVED หรือ COMPLETED โดยอัตโนมัติ

### User Story 3 - ดูประวัติใบตรวจรับสินค้าและการตรวจรับโดยตรง (Priority: P3)

ในฐานะผู้จัดการร้าน ฉันต้องการดูประวัติใบตรวจรับสินค้าทั้งหมด (Goods Receipts List) ตรวจสอบประวัติการรับสินค้า และรองรับการบันทึกตรวจรับตรงในกรณีฉุกเฉิน (Direct Goods Receipt โดยไม่ต้องมี PO ล่วงหน้า)

**Why this priority**: ให้ความยืดหยุ่นในกรณีร้านค้าจำเป็นต้องรับของด่วนจากผู้ผลิตในพื้นที่ และมีประวัติเอกสารอ้างอิงใบเสร็จ/ใบกำกับจากผู้จัดจำหน่าย

**Independent Test**: สามารถเปิดดูรายการใบตรวจรับ กรองตามช่วงวันที่/ซัพพลายเออร์ ดูรายละเอียดใบรวดเร็ว และสามารถสร้างใบตรวจรับตรงได้

**Acceptance Scenarios**:

1. **Given** ผู้ใช้อยู่ในหน้ารายการใบตรวจรับสินค้า  
   **When** ค้นหาด้วยเลขที่ใบตรวจรับ เลขที่ใบสั่งซื้อ หรือเลขที่ใบกำกับภาษีของผู้จำหน่าย (`supplierInvoiceNo`)  
   **Then** แสดงรายการใบตรวจรับตรงตามเงื่อนไข พร้อมสถานะ (DRAFT, COMPLETED, CANCELLED)
2. **Given** ผู้ใช้ต้องการบันทึกรับสินค้าเข้าคลังแบบไม่มีใบสั่งซื้อ  
   **When** เลือกสร้างใบตรวจรับแบบกำหนดเอง ระบุผู้จัดจำหน่ายและรายการสินค้า  
   **Then** สามารถบันทึกตรวจรับและนำยอดเข้าสต็อกได้ถูกต้อง

---

### Out of Scope (ขอบเขตที่ยังไม่รวมในระยะนี้)

- **การพิมพ์ใบลดหนี้/ใบเพิ่มหนี้ทางบัญชี**: ให้จัดการผ่านระบบบัญชีแยกต่างหาก
- **การส่งอีเมล/ใบ PO เป็น PDF ไปยัง Supplier โดยอัตโนมัติ**: มุ่งเน้นการบันทึกเอกสารและโฟลว์ในระบบ POS/คลังก่อน
- **การเชื่อมต่อเครื่องพิมพ์สติกเกอร์บาร์โค้ดล็อตสินค้า**: จัดเก็บข้อมูล Lot และ Expiry ในฐานข้อมูล แต่ยังไม่มีคำสั่งพิมพ์ฉลากเฉพาะทาง

---

### Edge Cases

- **การรับสินค้าบางส่วน (Partial Delivery)**: เมื่อผู้จัดจำหน่ายส่งสินค้าเพียงบางส่วน ระบบต้องรองรับการสร้างใบตรวจรับหลายครั้งสำหรับใบสั่งซื้อใบเดียว จนกว่าจะครบยอด หรือจนกว่าผู้ใช้จะกดบังคับปิดใบสั่งซื้อ (`POST /purchase-orders/{id}/close`)
- **การรับสินค้าเกินจำนวนที่สั่ง (Over-delivery)**: ระบบต้องแสดงคำเตือนเมื่อจำนวนที่ระบุรับจริงมากกว่าจำนวนที่สั่งซื้อใน PO
- **สินค้าเสียหาย 100%**: รองรับกรณีที่รับสินค้าไม่ได้เลยเนื่องจากชำรุดทั้งล็อต โดยระบุจำนวนรับเป็น 0 และจำนวนคัดทิ้งเท่ากับยอดที่ส่ง พร้อมระบุเหตุผล
- **การกดส่งคำขอซ้ำหรือเน็ตหลุดระหว่างยืนยัน**: ต้องมี Loading Overlay บล็อกหน้าจอ และส่งคีย์ป้องกันการทำซ้ำ (Idempotency) เพื่อไม่ให้เกิดการเพิ่มยอดสต็อกเบิ้ล
- **ยกเลิกใบตรวจรับที่ยืนยันแล้ว**: API อนุญาตการยกเลิกเฉพาะสถานะ DRAFT หาก COMPLETED แล้วต้องจัดการผ่านการปรับยอดสต็อก (Stock Adjustment) เท่านั้น

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: ระบบ MUST จัดเตรียมแท็บการทำงานบนหน้าเว็บ `/inventory` ประกอบด้วย 3 แท็บหลัก ได้แก่ "สต็อกสินค้าคงเหลือ", "ใบสั่งซื้อสินค้า (PO)" และ "ตรวจรับสินค้าเข้าคลัง (GR)" ภายใต้ Layout หลัก พร้อมจำกัดสิทธิ์เฉพาะผู้ใช้บทบาท `ADMIN` และ `MANAGER`
- **FR-002**: ระบบ MUST ดึงข้อมูลรายการใบสั่งซื้อสินค้าจาก API `GET /api/v1/purchase-orders` พร้อมรองรับตัวกรองตามสาขา (`branchId`), ซัพพลายเออร์ (`supplierId`), สถานะ (`status`), ช่วงวันที่ (`startDate`, `endDate`), คำค้นหา (`search`) และการแบ่งหน้า (`page`, `limit`)
- **FR-003**: ระบบ MUST มีฟอร์มสร้างใบสั่งซื้อใหม่ส่งคำขอไปยัง `POST /api/v1/purchase-orders` โดยระบุสาขา, ผู้จัดจำหน่าย, วันที่สั่งซื้อ, กำหนดส่งมอบ, หมายเหตุ, รายการสินค้า (รหัสสินค้า, จำนวน, หน่วยนับ, ต้นทุนต่อหน่วย, หมายเหตุ) และสถานะเริ่มต้น (DRAFT หรือ ORDERED)
- **FR-004**: ระบบ MUST รองรับการดูรายละเอียดใบสั่งซื้อ `GET /api/v1/purchase-orders/{id}`, แก้ไขใบสั่งซื้อ `PUT /api/v1/purchase-orders/{id}` (เฉพาะสถานะ DRAFT), ยืนยันการสั่งซื้อ `POST /api/v1/purchase-orders/{id}/confirm`, ยกเลิก `POST /api/v1/purchase-orders/{id}/cancel` และบังคับปิด `POST /api/v1/purchase-orders/{id}/close`
- **FR-005**: ระบบ MUST มีฟังก์ชันดึงรายการสินค้าที่ยังค้างรับในใบสั่งซื้อผ่าน API `GET /api/v1/purchase-orders/{id}/receipt-preview` เพื่อนำมาเตรียมข้อมูลสร้างใบตรวจรับสินค้าได้ในคลิกเดียว
- **FR-006**: ระบบ MUST ดึงข้อมูลรายการใบตรวจรับสินค้าจาก API `GET /api/v1/goods-receipts` พร้อมตัวกรองสถานะ, สาขา, ซัพพลายเออร์, เลขที่ใบสั่งซื้อ และการแบ่งหน้า
- **FR-007**: ระบบ MUST มีฟอร์มสร้างใบตรวจรับสินค้าเข้าคลังผ่าน API `POST /api/v1/goods-receipts` รองรับทั้งการอ้างอิงใบสั่งซื้อ (`purchaseOrderId`) และการรับตรง ระบุเลขที่ใบแจ้งหนี้/ใบส่งของ (`supplierInvoiceNo`), วันที่รับมอบ, รายการสินค้า (จำนวนรับจริง `receivedQuantity`, จำนวนคัดทิ้ง `rejectedQuantity`, เหตุผลคัดทิ้ง `rejectReason`, เลขล็อต `lotNumber`, วันหมดอายุ `expiryDate`, ต้นทุน `unitCost`)
- **FR-008**: ระบบ MUST รองรับการยืนยันการตรวจรับสินค้าเข้าคลังผ่าน API `POST /api/v1/goods-receipts/{id}/complete` เพื่อปรับปรุงยอดสต็อกสินค้าคงคลังจริง
- **FR-009**: ระบบ MUST รองรับการยกเลิกใบตรวจรับสินค้าผ่าน API `POST /api/v1/goods-receipts/{id}/cancel` (สำหรับสถานะ DRAFT)
- **FR-010**: ระบบ MUST ดึงข้อมูลผู้จัดจำหน่ายจาก API `GET /api/v1/suppliers` เพื่อนำมาแสดงใน Dropdown สำหรับเลือกซัพพลายเออร์
- **FR-011**: ทุกการเรียก API ที่เกิดจากการกดของผู้ใช้ (สร้าง/แก้ไข/ยืนยัน/ยกเลิก) ระบบ MUST แสดง Loading Overlay บล็อกการคลิกซ้ำจนกว่าการทำงานจะเสร็จสิ้นตามข้อกำหนดธรรมนูญข้อ 6.6
- **FR-012**: ปุ่มและองค์ประกอบสัมผัสต้องมีขนาดไม่เล็กกว่า 48x48px และใช้ภาษาไทยที่ชัดเจนตามข้อกำหนดธรรมนูญข้อ 6.5 และ 2.1
- **FR-013**: ในหน้าจอตรวจรับสินค้าเข้าคลัง ระบบ MUST มีปุ่มเปิดกล้องสแกนบาร์โค้ดสินค้า (นำคอมโพเนนต์ `BarcodeCaptureModal` มาใช้ซ้ำ) โดยเมื่อตรวจพบบาร์โค้ดที่ตรงกับรายการสินค้าในใบตรวจรับ ระบบจะบวกเพิ่มจำนวนรับจริง (`receivedQuantity`) ขึ้นทีละ 1 โดยอัตโนมัติ พร้อมอนุญาตให้แก้ไขตัวเลขด้วยการพิมพ์ในช่องได้ตลอดเวลา
- **FR-014**: ในกรณีที่จำนวนสินค้าตรวจรับจริง (`receivedQuantity`) เกินกว่าจำนวนที่ระบุในใบสั่งซื้อ ระบบ MUST แสดงกล่องข้อความเตือน (Warning Confirmation Dialog) ภาษาไทยระบุจำนวนที่เกิน เพื่อให้ผู้ใช้กดยืนยันการรับเกินก่อนส่งคำขอบันทึก

### Key Entities *(include if feature involves data)*

- **PurchaseOrder**: ข้อมูลใบสั่งซื้อสินค้า ประกอบด้วย รหัส (`id`), เลขที่ใบสั่งซื้อ (`poNumber`), รหัสสาขา (`branchId`), รหัสผู้จัดจำหน่าย (`supplierId`), สถานะ (`status`: DRAFT, ORDERED, PARTIALLY_RECEIVED, COMPLETED, CANCELLED), วันที่สั่งซื้อ (`orderDate`), กำหนดวันส่งมอบ (`expectedDeliveryDate`), ยอดรวมสุทธิ (`totalAmount` หน่วยสตางค์), ภาษี (`taxAmount`), หมายเหตุ (`note`), รายการสินค้า (`lines`)
- **PurchaseOrderLine**: รายการสินค้าในใบสั่งซื้อ ประกอบด้วย รหัส (`id`), รหัสสินค้า (`productId`), ข้อมูลสินค้า (`product`), จำนวนที่สั่ง (`quantity`), จำนวนที่รับแล้ว (`receivedQuantity`), หน่วยนับ (`uomId`), ราคาต้นทุนต่อหน่วย (`unitCost` หน่วยสตางค์), หมายเหตุ (`note`)
- **GoodsReceipt**: ข้อมูลใบตรวจรับสินค้า ประกอบด้วย รหัส (`id`), เลขที่ใบตรวจรับ (`receiptNumber`), รหัสสาขา (`branchId`), รหัสใบสั่งซื้ออ้างอิง (`purchaseOrderId`), รหัสผู้จัดจำหน่าย (`supplierId`), เลขที่ใบส่งของ/ใบกำกับ (`supplierInvoiceNo`), วันที่ตรวจรับ (`receivedDate`), สถานะ (`status`: DRAFT, COMPLETED, CANCELLED), รายการสินค้าตรวจรับ (`lines`), หมายเหตุ (`note`)
- **GoodsReceiptLine**: รายการสินค้าที่ตรวจรับ ประกอบด้วย รหัส (`id`), รหัสสินค้า (`productId`), ข้อมูลสินค้า (`product`), จำนวนที่รับจริง (`receivedQuantity`), จำนวนที่ปฏิเสธ/คัดทิ้ง (`rejectedQuantity`), เหตุผลคัดทิ้ง (`rejectReason`), เลขล็อต (`lotNumber`), วันหมดอายุ (`expiryDate`), ต้นทุนต่อหน่วย (`unitCost`), รหัสรายการสั่งซื้ออ้างอิง (`purchaseOrderLineId`)
- **Supplier**: ข้อมูลผู้จัดจำหน่าย ประกอบด้วย รหัส (`id`), ชื่อผู้จัดจำหน่าย (`name`), รหัสโค้ด (`code`), เบอร์โทรศัพท์ (`phone`), อีเมล (`email`), ที่อยู่ (`address`), สถานะการใช้งาน (`isActive`)

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ผู้ใช้สามารถสร้างและยืนยันใบสั่งซื้อสินค้า (PO) ได้เสร็จสิ้นภายในเวลาไม่เกิน 2 นาที
- **SC-002**: ผู้ใช้สามารถดึงข้อมูลสินค้าค้างรับจากใบสั่งซื้อและทำการตรวจรับเข้าสต็อก (GR) ได้ภายในเวลาไม่เกิน 90 วินาที
- **SC-003**: ข้อมูลยอดสต็อกคงเหลือในระบบอัปเดตตรงตามยอดรับจริงในใบตรวจรับที่ได้รับการยืนยัน (COMPLETED) 100% โดยไม่มีข้อผิดพลาด
- **SC-004**: ระบบแสดง Loading Overlay บล็อกการกดซ้ำได้ 100% ในทุกขั้นตอนการสร้าง ยืนยัน หรือยกเลิกเอกสาร PO และ GR

## Assumptions

- ระบบใช้งาน Backend API ตามเอกสาร Swagger ที่มี Endpoint `/api/v1/purchase-orders`, `/api/v1/goods-receipts` และ `/api/v1/suppliers`
- การป้อนราคาและมูลค่าเงินในระบบใช้หน่วยสตางค์ (Satang) ในการส่งข้อมูลไปยัง API และแปลงเป็นบาท (THB) ในการแสดงผลบนหน้าจอ
- การเข้าถึงโมดูลนี้ถูกจำกัดไว้สำหรับบทบาทผู้จัดการร้าน (MANAGER) และผู้ดูแลระบบ (ADMIN)
- ข้อมูลสาขาปัจจุบันดึงมาจากระบบ Context / State ของผู้ใช้งานที่ล็อกอินอยู่
